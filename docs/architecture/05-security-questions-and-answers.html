ক্লায়েন্ট, অডিটর বা ম্যানেজমেন্ট যেসব প্রশ্ন সাধারণত করে, তার উত্তর। প্রতিটি উত্তরের পাশে অবস্থা: ✅ আছে (কোড/টেস্টে প্রমাণসহ) · ⚠️ আংশিক · ❌ নেই · 🏢 প্রতিষ্ঠান/হোস্টিংয়ের ব্যাপার (সফটওয়্যারের কোডে নয়, আপনাদের সার্ভার/নীতিতে ঠিক করতে হবে)। প্রমাণের জায়গা: 04-security.md এবং docs/test-logs/। যা নেই তা "আছে" বলবেন না। অডিটে সেটাই সবচেয়ে বড় ঝুঁকি।

ক. পরিচয় যাচাই ও লগইন

প্রশ্ন উত্তর অবস্থা
কর্মীরা কী দিয়ে লগইন করে? দুজনের একই ID হতে পারে? নিজের Employee ID (যেমন CPL-0201), বা ইমেইল। একই Login ID দুজনের হতে পারে না: ডাটাবেসে UNIQUE, আর নতুন বা বদলানো Employee ID অন্য কারও ID/username/email-এর সাথে মিললে সার্ভার রাজি হয় না। ✅
পাসওয়ার্ড কীভাবে রাখা হয়? bcrypt hash (cost 10)। সরল পাসওয়ার্ড কোথাও রাখা হয় না, লগেও না। ✅
কেউ পাসওয়ার্ড অনুমান করলে? ৫ বার ভুলে অ্যাকাউন্ট ১৫ মিনিট লক, এক IP থেকে ৩০ বার ভুলে অপেক্ষা। আগে সফল login হওয়া (চেনা) ডিভাইস এই লকে আটকায় না, তার নিজের সীমা ১৫ মিনিটে ১০ বার। সব চেষ্টা login_attempts-এ। আমাদের টেস্টে ২৫ বার ভুলের পর আটকেছে। ✅
পাসওয়ার্ডের নীতি কী? কোম্পানির সিদ্ধান্তে যেকোনো পাসওয়ার্ড চলে (ব্যবহারকারীর সুবিধার জন্য)। এর বদলে: ২৫ বার ভুল হলে লগইন আটকে যায়, এক অ্যাকাউন্ট এক ফোনে, পাসওয়ার্ড বদলালে অন্য সব সেশন বন্ধ, পাসওয়ার্ড bcrypt hash-এ রাখা, চাইলে fingerprint/passkey। ⚠️ (জেনেশুনে নেওয়া ঝুঁকি)
Two-factor (2FA/MFA) আছে? সাধারণ লগইনে TOTP/SMS 2FA নেই। বিকল্প: Passkey/Fingerprint লগইন (ফোনে hardware-সুরক্ষিত), মোবাইলে "একটি ফোন" নিয়ম, ই-স্বাক্ষরে ইমেইল OTP। ⚠️
পাসওয়ার্ড ভুলে গেলে? ইমেইলে ৬ অঙ্কের কোড (১৫ মিনিট, ৫ চেষ্টা) অথবা HR অস্থায়ী পাসওয়ার্ড দেয়। দুটোতেই পুরোনো সব সেশন বন্ধ। কে অ্যাকাউন্ট আছে তা বোঝা যায় না। ✅
লগইন কতক্ষণ থাকে? ওয়েবে ১২ ঘণ্টা বা ৬০ মিনিট নিষ্ক্রিয় হলে শেষ; অ্যাপে ৭ দিন বা ৩ দিন না খুললে। Superadmin বদলাতে পারে। ✅
চাকরি ছাড়লে বা সন্দেহ হলে লগইন বন্ধ হয়? হ্যাঁ। ব্লক, পদত্যাগ/বরখাস্ত কার্যকর, বা Superadmin-এর "sign out" হলে সব সেশন সঙ্গে সঙ্গে বন্ধ (প্রতি রিকোয়েস্টে যাচাই)। ✅
পাসওয়ার্ড বদলালে চুরি যাওয়া সেশনের কী হয়? বাকি সব সেশন বন্ধ হয় (যে সেশন থেকে বদলানো সেটা থাকে)। ✅
Single Sign-On আছে? 360 ERP-এর সাথে SSO হস্তান্তর আছে (সার্ভার-টু-সার্ভার, গোপন চাবি ব্রাউজারে যায় না)। অন্য Identity Provider (Azure AD, Google) নেই। ⚠️

খ. অনুমতি ও গোপনীয়তা

প্রশ্ন উত্তর অবস্থা
কর্মী কি অন্যের SIM/ID card request দেখতে বা নিজে issue করতে পারে? না। কর্মী শুধু নিজের request দেখেন ও বাতিল করেন (সুইচ ডিফল্টে বন্ধ); issue বা turn down শুধু HR Operations-এর আলাদা requisitions layer দিয়ে, যা ডিফল্টে কারও নেই। নতুন joiner-এর request-এর route শুধু onboarding login খুলতে পারে, আর approve না হওয়া পর্যন্ত কিছু issue হয় না। ✅
কে কী দেখবে তা কীভাবে নিয়ন্ত্রণ হয়? তিন ভূমিকা (Superadmin/Admin/কর্মী) + ৪০ মডিউল + মডিউলের ভেতরে layer + বিভাগ-সীমা + কোম্পানি-সীমা। সব সার্ভারে প্রয়োগ হয় (UI লুকানো ছাড়াও API বন্ধ)। ✅
বেতনের তথ্য কে দেখে? শুধু Payroll মডিউলের Admin। কর্মী শুধু নিজের payslip। টেস্টে কর্মী অন্যের payroll খুলতে পারেনি। ✅
একজন একাই বেতন বানিয়ে পরিশোধ করতে পারে? না। HR বানায় → Audit অনুমোদন → Accounts পরিশোধ। যে বেতন চালিয়েছে/বদলেছে বা submit করেছে সে অনুমোদন দিতে পারে না; যে চালিয়েছে, submit বা অনুমোদন করেছে সে পরিশোধ করতে পারে না। Audit/Accounts "View only" layer পায় (দেখে, বদলাতে পারে না)। Audit Manager টেস্ট ৪৯/৪৯ পাস (test-logs/2026-10-25/06-audit-manager-retest.log)। ব্যতিক্রম: Superadmin। ⚠️
পদাধিকার বাড়িয়ে নেওয়া যায়? কর্মী নিজের role বাড়াতে পারে না; Admin নিজেকে বেশি মডিউল দিতে পারে না; API দিয়ে নতুন Superadmin বানানো যায় না (সবই টেস্টে যাচাই)। ✅
একাধিক কোম্পানির ডাটা আলাদা থাকে? হ্যাঁ, কোডে প্রতিটি SQL-এ কোম্পানির ফিল্টার বসে। (ডাটাবেস-স্তরে আলাদা স্কিমা নেই, একই ডাটাবেসে।) ⚠️
ব্যক্তিগত তথ্য (NID, ঠিকানা) কে দেখে? Employees মডিউলের Admin সব কর্মীর NID দেখেন; Employee Directory-তে সবাই সবার ফোন নম্বর দেখে। নীতি ঠিক করা দরকার। ⚠️
Employee Tracking-এ কে কার লোকেশন দেখে? Module Access-এ প্রতিটা অ্যাকাউন্টের জন্য বিভাগ আর একক কর্মী বাছা যায়; বাছা থাকলে সার্ভার শুধু তাঁদের লোকেশন, ইতিহাস, Stay Report ও Live Follow দেয়, অন্য কারও id দিলে 403। কিছু বাছা না থাকলে মডিউলের সবাইকে দেখে (আগের মতো); Superadmin সবসময় সবাই। ✅
একই ফোনে অন্য account-এ ঢুকলে আগের জনের ছবি বা তথ্য দেখায়? না। নিজের profile ছবির URL আর browser-এ cache হয় না, আর account বদলালেই আগের ছবি মুছে যায়। ✅
কেউ কি নিজের profile ছবি যা খুশি বদলে দিতে পারে? না। নতুন ছবি Superadmin-এর অনুমোদনের অপেক্ষায় থাকে, ততক্ষণ পুরনো ছবি দেখায়; Superadmin পুরনো-নতুন পাশাপাশি দেখে Approve বা কারণসহ Reject করেন। অনুমোদনের API শুধু Superadmin-এর (টেস্টে অন্য admin 403)। ✅
Payroll-এ MD অ্যাপ ব্যবহার না করলে তাঁর অনুমোদনের প্রমাণ কী? HR তাঁর সই/দাগ দেওয়া কাগজের scan/photo attach না করলে মাস এগোয় না; প্রতিটি print-এর version নম্বর পাতায় ছাপা; MD-র প্রতিটি বদল আলাদা correction হিসেবে (কে লিখল, কে apply করল, আগে-পরে net) থাকে আর history-তে সব ধাপ। ফাইল public ফোল্ডারে নয়, শুধু অনুমোদনের পথের layer দিয়ে খোলা যায়। ✅
Payroll-এ HR Director, Accounts, Audit কি নিজের বানানো বেতন পাস করতে পারেন? না। যে বেতন চালিয়েছে/বদলেছে বা মাস পাঠিয়েছে সে HR Director review দিতে পারে না; যে পাঠিয়েছে বা Accounts-এ পাঠিয়েছে সে pay করতে পারে না; যে বানিয়েছে, পাঠিয়েছে বা pay করেছে সে audit করতে পারে না (Superadmin ছাড়া)। Audit এখন টাকা দেওয়ার পরে, ঐচ্ছিক। ✅
Payroll-এর Top Sheet (সাইট-ভিত্তিক বেতন) কে দেখে? যাঁর Payroll module-এ "Approval — Top Sheet (view)" layer আছে (layer সেভ না থাকা Payroll ব্যবহারকারী ডিফল্টে পান; Audit / Accounts-এর "View only" থাকলে আলাদা টিক লাগে), আর Superadmin। API আর পাতার অংশ দুটোই এই layer দেখে; টেস্টে layer ছাড়া 403। এটা শুধু দেখা — approve / pay আগের নিয়মেই। ✅
HR-এর Custom attendance report বা AI Assistant দিয়ে কি সীমার বাইরের department-এর হাজিরা দেখা যায়? না। Attendance Report Builder আলাদা layer custom_report-এর পেছনে (API ও ট্যাব দুটোই), ডাটা আসে Monthly report-এর একই হিসাব থেকে, তাই Department সীমা ও কোম্পানি ফিল্টার একই থাকে। Assistant একই API প্রশ্নকারীর token দিয়ে ডাকে। টেস্টে layer ছাড়া Admin 403 পেয়েছেন, HR-সীমিত Admin Finance চাইলে খালি পেয়েছেন। ✅
লোকেশন ট্র্যাকিং কি সম্মতি ছাড়া? না। আলাদা সুইচ (ডিফল্ট বন্ধ) ও ব্যবহারকারীকে নোটিশ ও সম্মতির পেজ। ✅
কর্মী কি নিজের Out Time পরে বদলে বাড়িয়ে নিতে পারে? শুধু একই দিনে, শুধু Module Access-এ "Remote Attendance — update Out Time" টিক দেওয়া থাকলে (শুরুতে বন্ধ; কর্মী নিজে চালু করতে পারেন না, API 403), আর সেই সময়টাতেই project-এর এলাকায় থেকে — পরে বসে আগের সময় লেখা যায় না, সময় server-এর। প্রথম Out Time রাখা থাকে, নতুনটা আবার অনুমোদনে যায় (AttendanceRoutes.ts)। ✅
Remote check-in-এ কেউ কি অন্য project-এ বা মেয়াদ শেষের পর check-in করতে পারে? না। Module Access-এ দেওয়া project-এর তালিকা আর প্রতিটার From / To তারিখ server যাচাই করে — check-in, Correct Attendance ও Data Import-এ; অন্য project বা তারিখের বাইরে হলে 403। তালিকা বদলাতে Users module-এর edit_add layer লাগে, বদল user_access_audit-এ (AttendanceProjects.ts)। ✅
দূরের সাইটের ZKTeco মেশিন internet-এ punch পাঠায় — কেউ ভুয়া punch পাঠাতে পারে? ADMS protocol-এ password নেই, তাই শুধু register করা চালু মেশিনের Serial number মানা হয়, আর সাইটের IP দিলে শুধু সেখান থেকে; অচেনা SN-এর কিছু লেখা হয় না, শুধু punch নেওয়া হয়, মেশিনে কোনো command যায় না। SN জেনে IP-সীমা ছাড়া মেশিন নকল করা সম্ভব — তাই fixed IP থাকলে দেওয়ার পরামর্শ (zkMachines.ts, 04 §১০ নং ১৩)। ⚠️
এক মেশিনের PIN অন্য মেশিনের কারও হাজিরায় চলে যায় না? "Its own numbers" ধরনের মেশিনে প্রতিটা PIN আলাদা করে link হয় (zk_device_pins); link না হলে punch কারও হাজিরায় যায় না। link / unlink শুধু Office Attendance-এর "Link Device PINs" layer-এর (API 403, UI লুকানো)। ✅

ট্রানজিটে (ইন্টারনেটে) এনক্রিপশন? সার্ভার Nginx-এর পেছনে HTTPS-এ চালানোর কনফিগ আছে (deploy/nginx.conf.example), HTTPS হলে HSTS যায়। সার্টিফিকেট বসানো আপনাদের কাজ। 🏢
Chat-এর voice / ছবি / video / document কোথায় থাকে, অন্য কেউ খুলতে পারে? server-এর একটা folder-এ (.env-এর CHAT_ATTACHMENT_DIR), ডাটাবেসে শুধু path। folder ওয়েবে খোলা নয় — ফাইল যায় শুধু সেই chat-এর সদস্যের কাছে, অন্যরা 403। ফাইলের নাম এলোমেলো, আর path folder-এর বাইরে গেলে server খোলে না। Delete for everyone করলে ফাইলও মুছে যায়। folder-এর অনুমতি, disk এনক্রিপশন আর ব্যাকআপ হোস্টিংয়ের দায়িত্ব (chatFiles.ts)। ✅ 🏢
Notice-এর Animation library-তে কেউ ক্ষতিকর animation রাখতে পারে? যোগ / মোছা শুধু 🔒 notice_animations layer যাঁর (শুরুতে কারও নেই; API-তেও 403)। শুধু Lottie JSON নেওয়া হয় (৩ MB পর্যন্ত), আর ভেতরের expression — যেখানে JavaScript থাকতে পারে — server-এ বাদ দেওয়া হয়; app-এর light player expression চালায়ও না (NoticeSafety.ts)। ✅
Notice-এ দেওয়া ছবি বা PDF কি যে কেউ খুলতে পারে? কে পড়েছে কে দেখে? না। ফাইল server-এর folder-এ, ওয়েবে খোলা নয়; খোলে শুধু Notices module-এর লোক আর যাঁদের জন্য notice এখন live। শুধু ছবি ও অফিস-ডকুমেন্ট upload হয় (ছবির ভেতরের byte মিলিয়ে)। কে খুলেছেন / পড়েছেন সেই নাম-ধরা report শুধু notice_read_report layer যাঁর, আর notice email করা শুধু notice_email layer — দুটোই শুরুতে কাউকে দেওয়া থাকে না, API-তেও 403 (NoticeRoutes.ts)। ✅
রেস্টে (ডাটাবেস/ডিস্কে) এনক্রিপশন? অ্যাপ নিজে পুরো ডাটাবেস এনক্রিপ্ট করে না। নির্দিষ্ট সিক্রেট এনক্রিপ্ট/hash: মেইল পাসওয়ার্ড (AES-256-GCM), সব পাসওয়ার্ড (bcrypt), token/কোড (hash)। ডিস্ক এনক্রিপশন হোস্টিংয়ে। ⚠️ 🏢
ফোনে কি অ্যাপের data জমা থাকে? অন্য কেউ ওই ফোনে login করলে দেখবে? Dashboard তাড়াতাড়ি খোলার জন্য নিজের কার্ডগুলোর শেষ data ফোনে / ব্রাউজারে থাকে (অন্য কর্মীদের location বা Tracking-এর তালিকা নয়)। অ্যাকাউন্ট ও কোম্পানি আলাদা করে রাখা হয়, logout বা নতুন login-এ মুছে যায়, ৭ দিনের বেশি পুরোনো হলে ব্যবহার হয় না। নতুন data সবসময় server থেকে অনুমতি যাচাই করে আসে। ✅
Chat group-এ কে নাম / photo / setting বদলাতে পারে? Starred বা Clear chat কি অন্যরা দেখে? Group admin (setting অনুযায়ী member-ও নাম / photo / description); "Only admins can send" চালু থাকলে member-এর message server-ই আটকায়। Star, Mute ও Clear chat শুধু নিজের জন্য, অন্য কারো chat-এ কিছু বদলায় না। ✅
Chat group-এর invite link বাইরের কেউ পেলে কী হবে? Disappearing message কি সত্যিই মুছে যায়? Link দিয়ে যোগ দিতে CredenceHR-এ login আর Chat-এর অনুমতি লাগে, তাই কোম্পানির বাইরের কেউ পারে না; admin link reset বা বন্ধ করলে পুরোনোটা আর কাজ করে না, আর কে link দিয়ে এসেছে তা group-এ লেখা থাকে। Disappearing message সময় পেরোলেই কারো কাছে দেখায় না, আর কয়েক মিনিটের মধ্যে ডাটাবেস ও ফাইল থেকে মুছে যায় (আগে নেওয়া ব্যাকআপে থাকতে পারে)। ✅
Group call-এ বাইরের কেউ ঢুকতে বা শুনতে পারে? Call কি রেকর্ড হয়? না। শুধু group-এর member যাঁদের Calls অনুমতি আছে তাঁরাই ঢুকতে পারেন, আর কে আছেন তা call-এ সবার পর্দায় দেখায়। Audio / video ফোন থেকে ফোনে এনক্রিপ্ট হয়ে যায়; server কিছু রেকর্ড বা জমা করে না, শুধু শুরু ও শেষের সময় chat-এ লেখা থাকে। ✅
অফিস / project-এর বাইরে থেকে কেউ হাজিরা দিলে কী হয়? দেওয়া যায়, কিন্তু কারণ লিখতে হয় আর সেটা হাজিরা হিসেবে গোনা হয় শুধু supervisor-দের approval chain approve করলে; কোথা থেকে দেওয়া (GPS, দূরত্ব) approver দেখেন। Reject হলে কিছুই গোনা হয় না। ✅
বেতন দেওয়া হয়ে গেলে কেউ সেই মাসের হাজিরা বদলাতে পারে? না। বেতন Processed বা Paid হলে সেই মাসের সংশোধনের আবেদন নেওয়া হয় না, আর আগের অপেক্ষায় থাকা আবেদনও approve করা যায় না (শুধু reject)। ✅
SQL Injection থেকে সুরক্ষা? সব query prepared statement। লগইনে injection চেষ্টা টেস্টে আটকেছে। ✅
XSS থেকে সুরক্ষা? React নিজে escape করে; Notice-এর HTML সার্ভার ও ব্রাউজারে পরিষ্কার। টেস্ট: <script>/onerror ফেরে না। ✅
ফাইল আপলোড নিরাপদ? আকার সীমিত (২৫–৩০MB), ছবির ধরন যাচাই। ডকুমেন্টের ধরন-যাচাই ও ভাইরাস স্ক্যান নেই। ⚠️
ভুল বা ডাটাবেসের ত্রুটি ব্যবহারকারী দেখে? না। ডাটাবেসের বার্তা লুকানো, সংক্ষিপ্ত সাধারণ বার্তা যায়। ✅
এক কোম্পানির HR অন্য কোম্পানির কর্মীর তথ্য দেখতে পারে? না। Admin Panel-এর কাজে id দিয়ে খুললেও শুধু চলতি কোম্পানির (বা সেখানে assign করা) কর্মী পাওয়া যায়; অন্য কোম্পানির ব্যাংক অ্যাকাউন্ট, বেতন, নাম পড়া/বদলানো আটকায় (টেস্ট qa-companies ১৮/১৮)। ✅
মাদার কোম্পানির HR কি sister company-গুলোর কাজও করতে পারেন? হ্যাঁ, Superadmin প্রবেশাধিকার দিলে: company switcher-এ কোম্পানি বেছে, অথবা আলাদা অনুমতি "All companies mode" দিলে সব কোম্পানির কর্মীর রেকর্ড এক জায়গা থেকে। দুটোই Superadmin-এর হাতে, ডিফল্টে বন্ধ, আর বদল নিরীক্ষা লগে থাকে (টেস্ট qa-group-hr ২১/২১)। ✅
একসাথে দুবার ক্লিক করলে বেতন/বিল দুবার যায়? না। অনুমোদন, বেতন পরিশোধ, বিল disburse, ঋণ অনুমোদন ডাটাবেসে শর্ত দিয়ে একবারই হয়; দ্বিতীয়টা 409 পায় (টেস্ট qa-concurrency ৯/৯)। ✅
গুরুত্বপূর্ণ রেকর্ড ভুলে মুছে যেতে পারে? কর্মী মুছতে গেলে বেতন/সেবা-রেকর্ড থাকলে আটকায় (ডাটাবেসও আটকায়)। পরিশোধিত বেতন বদলানো যায় না। ✅
ব্যাকআপ? সফটওয়্যারে ডাটাবেস ব্যাকআপের স্বয়ংক্রিয় ব্যবস্থা নেই। ফাইলও ডাটাবেসে, তাই ডাটাবেস ব্যাকআপই সব। MySQL dump/স্ন্যাপশট সময়সূচি আপনাদের ঠিক করতে হবে। 🏢 ❌
ডিজাস্টার রিকভারি (RTO/RPO)? লিখিত পরিকল্পনা নেই। 🏢 ❌

ঘ. নিরীক্ষা ও লগ

প্রশ্ন উত্তর অবস্থা
কে কী করেছে তার প্রমাণ থাকে? লগইন চেষ্টা, পাসওয়ার্ড রিসেট, অ্যাক্সেস বদল, payroll-এ প্রতিটি লেখা, কর্মীর তথ্য বদল (আগে/পরে), বেতনের ব্যাংক অ্যাকাউন্ট বদল (কর্মীকে alert সহ), ই-স্বাক্ষর ঘটনা, MPR সম্পাদনা, Mail অ্যাডমিন কাজ। 04-security.md §৮। ✅
অনুমোদনের মাঝখানে কেউ নিজের ইচ্ছামতো অন্য কাউকে approver বানাতে পারে? শুধু সেই মুহূর্তে যে Layer-এর approver, এবং যাঁর Module Access-এ Approvals — add an ad-hoc approver (users.can_add_adhoc_approver, শুরুতে বন্ধ) চালু; Superadmin সবসময়। আবেদনকারী নিজে বা নিজেকে বাছা যায় না, একসাথে একজনই, কারণ লেখা বাধ্যতামূলক; server-এ যাচাই হয় (POST /api/my-approvals/:id/adhoc) এবং পুরো ঘটনা approval trail-এ থাকে। ✅
কোনো মডিউলের অনুমতি থাকলেই কি Excel দিয়ে একসাথে অনেক ডাটা ঢোকানো যায়? না। HR Data Import আলাদা মডিউল (data_import), আর প্রতিটি ধরন (Employee, Leave, Check In/Out, Conveyance, Remote/Office Attendance) আলাদা টিক — সব শুরুতে বন্ধ। মডিউল + সেই টিক দুটোই না থাকলে সার্ভার 403 দেয় (DataImportRoutes.ts)। Superadmin সবসময় পারেন। ✅
সব ডাটা-পড়ার লগ আছে? না। সব পেজ খোলার লগ নেই (শুধু Payroll-এ কে কোন পেজ খুলল আছে)। ⚠️
লগ কেন্দ্রীয়/অপরিবর্তনীয়? আলাদা SIEM/অপরিবর্তনীয় লগ নেই। অ্যাপ লগ PM2-তে। ❌
লগ কতদিন রাখা? login_attempts ৩০ দিন; বাকিগুলো মোছার স্বয়ংক্রিয় ব্যবস্থা দেখিনি (জমে থাকে)। নীতি ঠিক করা দরকার। ⚠️

ঙ. ই-স্বাক্ষর ও ডকুমেন্ট

প্রশ্ন উত্তর অবস্থা
স্বাক্ষর কি আইনত বৈধ? প্রযুক্তিগতভাবে: স্বাক্ষরকারী চেনা (OTP চালু করলে), ফাইলের SHA-256, সময়, ক্রম, QR দিয়ে যাচাই, ঐচ্ছিক PKCS#7 সার্টিফিকেট স্বাক্ষর। আইনি বৈধতার জন্য বাংলাদেশের CCA-অনুমোদিত সার্টিফিকেট কিনে (ESIGN_CERT_FILE) বসানো এবং আইনজীবীর মত লাগবে। বর্তমান সার্টিফিকেট self-signed হলে Adobe-এ "validity unknown" দেখাবে। ⚠️
স্বাক্ষরের পর ফাইল বদলালে ধরা যায়? হ্যাঁ। সার্টিফিকেট স্বাক্ষরে এক বাইট বদলালেও PDF reader ধরে; /verify পেজেও ফাইল মেলানো যায়। ✅

চ. বাইরের সেবা ও তৃতীয় পক্ষ

প্রশ্ন উত্তর অবস্থা
ডাটা কি বাইরের কোনো সেবায় যায়? শুধু যা .env-এ চালু করা হয়েছে: Google Gemini (AI Assistant, চালু থাকলে প্রশ্ন ও ফল Google-এ যায়, বন্ধ রাখা যায়; "AI Assistant — voice" যাঁর চালু তাঁর বলা প্রশ্নের রেকর্ডও লিখে নেওয়ার জন্য যায়, আমাদের কাছে জমা থাকে না), Firebase (পুশ নোটিফিকেশন, শিরোনাম/বার্তা), SMTP/IMAP (মেইল সার্ভার), CARTO (মানচিত্র টাইল), 360 ERP (SSO)। কোনোটাই বাধ্যতামূলক নয়। ✅
Analytics/ট্র্যাকার? তৃতীয় পক্ষের analytics নেই (নিজস্ব platform_visits টেবিল আছে)। ✅
থার্ড-পার্টি লাইব্রেরির তালিকা ও লাইসেন্স? dependency-sbom.csv (৭২৬ প্যাকেজ, লাইসেন্সসহ) ও 03-technology-and-libraries.md। অব্যবহৃত GPL-3.0 লাইব্রেরিটি (@mlightcad/libredwg-web) ২৫ অক্টোবর ২০২৬-এ বাদ দেওয়া হয়েছে। ✅

কীভাবে উত্তর দেবেন (পরামর্শ)

  1. সবসময় প্রমাণ দেখান: "আমরা নিরাপদ" বলার বদলে ফাইলের নাম বা টেস্ট লগ দেখান।
  2. যা নেই তা স্বীকার করুন এবং তারিখসহ পরিকল্পনা দিন। ❌ ও ⚠️ সারি ধরে একটি কর্মপরিকল্পনা বানিয়ে রাখুন।
  3. "হোস্টিং-নির্ভর" (🏢) প্রশ্নে আপনাদের সার্ভার প্রদানকারীর নথি (ডাটা সেন্টার, ব্যাকআপ, TLS) আলাদা দেখাতে হবে।
  4. অডিট আসার আগে: CORS_ORIGINS সেট, পাসওয়ার্ড নীতি নিয়ে লিখিত সিদ্ধান্ত (সহজ পাসওয়ার্ড কেন), ~~অব্যবহৃত GPL লাইব্রেরি বাদ~~ (✅ হয়ে গেছে), ব্যাকআপ পরীক্ষা (একবার পুনরুদ্ধার করে দেখা), penetration test বুক করা। এগুলো সবচেয়ে কম খরচে সবচেয়ে বেশি প্রশ্নের উত্তর বদলে দেয়।

প্রশ্ন: .env-এ CORS_ORIGINS দেওয়ার পরও সার্ভার "CORS_ORIGINS is not set" দেখাচ্ছিল কেন? উত্তর: .env লোড হওয়ার আগেই WebSecurity.ts মানটা পড়ে ফেলত, তাই তালিকা খালি ধরে নিয়ে CORS সবার জন্য খোলা রাখত। এখন .env সবার আগে লোড হয়, তাই তালিকাটা সত্যিই কাজ করে: তালিকার বাইরের সাইট API-র উত্তর পড়তে পারে না।

প্রশ্ন: কোনো কর্মী ওয়েবসাইটে যা পারেন, মোবাইল অ্যাপে কি তার চেয়ে কম দেওয়া যায়? উত্তর: হ্যাঁ। Module Access-এ প্রতিটা module আর Self Service switch-এর আলাদা App switch আছে, আর পুরো অ্যাপ বন্ধ করার একটা মূল switch। অ্যাপ কখনো ওয়েবসাইটের চেয়ে বেশি পায় না। এটা শুধু menu লুকানো না: অ্যাপের token দিয়ে বন্ধ module-এর API ডাকলে সার্ভার 403 দেয়, আর অ্যাপ বন্ধ থাকলে login-ই হয় না (AppAccess.ts)। নতুন অ্যাকাউন্টে অ্যাপ ডিফল্টে বন্ধ; প্রতিটা বদল access audit-এ থাকে।

প্রশ্ন: কল চলাকালে নেট কেটে আবার ফিরলে কেউ কি অন্যের কলে ঢুকে পড়তে পারে? উত্তর: না। কল ধরে রাখার ৩০ সেকেন্ডে ফিরে আসতে call:rejoin লাগে, আর server সেটা শুধু সেই কলের caller বা callee-র নিজের লগইন করা account থেকে নেয় (socket-এর token যাচাই করা user id দিয়ে, CallRoutes.ts)। অন্য কেউ চাইলে "This call has ended." পায়। কলের media আগের মতোই সরাসরি দুই ফোনের মধ্যে encrypted (DTLS-SRTP) থাকে।

প্রশ্ন: অ্যাপ বন্ধ অবস্থায় কল কাটার (Decline) route-এ sign-in লাগে না কেন, এটা কি ঝুঁকি? উত্তর: ফোনের কল-পর্দা অ্যাপ খোলা ছাড়াই চলে, তাই সেখানে sign-in token থাকে না। তার বদলে প্রতিটা কলের জন্য আলাদা ৪৮-অক্ষরের এলোমেলো চাবি তৈরি হয়, যা শুধু callee-র নিজের ফোনের push-এ যায়। চাবি ছাড়া বা ভুল চাবিতে কিছু হয় না; ঠিক চাবিতেও শুধু সেই বাজতে থাকা কলটা Decline হয় — কোনো ডাটা পড়া বা বদলানো যায় না (CallRoutes.ts)।

প্রশ্ন: Claim-এর না পাঠানো খসড়া ফোনে থাকে — একই ফোনে অন্য কেউ login করলে কি তা দেখতে পায়? উত্তর: না। খসড়া (src/lib/formDraft.ts) প্রতিটা account-এর আলাদা চাবিতে থাকে, তাই অন্য login সেটা পড়ে না; sign-out করলেই সব খসড়া মুছে যায়, পাঠালে বা ৩ দিন পরেও মুছে যায়। খসড়ায় শুধু নিজের লেখা থাকে (ফাইল নয়), আর পাঠানোর সময় server আগের মতোই সব অনুমতি ও হিসাব যাচাই করে — খসড়া কিছুই অনুমোদন করে না।

প্রশ্ন: "Conveyance Bill Claim" থেকে "Bill Claim" নাম বদলানোর পর কেউ কি অনুমতি হারায় বা বাড়তি পায়? উত্তর: না। Server চালু হওয়ার সময় (billClaimRename.ts) আগে দেওয়া প্রতিটা অনুমতি একই মানুষের কাছে নতুন নামে সরে যায়: Admin module conveyance → bill_claim, তার layer, Data Import-এর import_conveyance → import_bill_claims, Self Service switch can_view_conveyance_claims → can_view_bill_claims, App access আর Access Template-এর টিক। নতুন কিছু দেওয়া হয় না। পুরনো API (/api/user-claims) আর নেই, নতুন /api/bill-claims আগের মতোই module / layer / switch যাচাই করে।

প্রশ্ন: কারো Budget (PEPM) switch বন্ধ থাকলে সে কি API দিয়ে Budget বা MPR No-র তালিকা পড়তে পারে? উত্তর: না (৭ নভেম্বর ২০২৬ থেকে)। আগে menu লুকাত কিন্তু /api/budgets, budget item, MPR No, Job-এর তালিকা যেকোনো login করা account পেত — পুরো-অ্যাপ টেস্টে ধরা পড়ে। এখন requireBudgetRead শুধু Superadmin, Budget switch চালু, Job Edit, আর PEPM module (Imports, MPR Nos, Reports, Projects) থাকা Admin-কে দেয়; বাকিরা 403। Admin Dashboard-ও এখন শুধু দেওয়া module-এর tile দেখায় ও তার ডাটাই চায়।

প্রশ্ন: অফিসের সবাই একই internet (একই IP) থেকে আসেন। কয়েকজনের ভুল password-এ কি পুরো অফিস আটকে যাবে? আর কেউ কি আমার ID-তে ইচ্ছে করে ভুল দিয়ে আমাকে আটকে রাখতে পারে? উত্তর: যাঁরা আগে এই ফোন / browser থেকে সফলভাবে login করেছেন, তাঁরা আটকাবেন না। সফল login-এর পর ডিভাইসটা ওই account-এর জন্য একটা সই করা token পায় (চেনা ডিভাইস, LoginGuard.ts)। পরের login-এ সেটা থাকলে network-এর ৩০-বার আর account-এর ৫-বার লক ওই ডিভাইসে খাটে না; শুধু ডিভাইসের নিজের সীমা (১৫ মিনিটে ১০ বার ভুল)। অচেনা ডিভাইস (নতুন ফোন, অন্য কারো কম্পিউটার) আগের নিয়মেই আটকায়, তাই password অনুমান আগের মতোই কঠিন। Token নকল বা বদলানো যায় না (HMAC), অন্য account-এ কাজ করে না, ১৮০ দিন পরে বা password বদলালে বাতিল হয়।
