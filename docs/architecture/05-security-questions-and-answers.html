ক. পরিচয় যাচাই ও লগইন

প্রশ্ন উত্তর অবস্থা
কর্মীরা কী দিয়ে লগইন করে? দুজনের একই ID হতে পারে? নিজের Employee ID (যেমন CPL-0201), বা ইমেইল। একই Login ID দুজনের হতে পারে না: ডাটাবেসে UNIQUE, আর নতুন বা বদলানো Employee ID অন্য কারও ID/username/email-এর সাথে মিললে সার্ভার রাজি হয় না। ✅
পাসওয়ার্ড কীভাবে রাখা হয়? bcrypt hash (cost 10)। সরল পাসওয়ার্ড কোথাও রাখা হয় না, লগেও না। ✅
কেউ পাসওয়ার্ড অনুমান করলে? ৫ বার ভুলে অ্যাকাউন্ট ১৫ মিনিট লক, এক IP থেকে ৩০ বার ভুলে অপেক্ষা। আগে সফল login হওয়া (চেনা) ডিভাইস এই লকে আটকায় না, তার নিজের সীমা ১৫ মিনিটে ১০ বার। সব চেষ্টা login_attempts-এ। আমাদের টেস্টে ২৫ বার ভুলের পর আটকেছে। ✅
পাসওয়ার্ডের নীতি কী? কোম্পানির সিদ্ধান্তে যেকোনো পাসওয়ার্ড চলে (ব্যবহারকারীর সুবিধার জন্য)। এর বদলে: ২৫ বার ভুল হলে লগইন আটকে যায়, এক অ্যাকাউন্ট এক ফোনে, পাসওয়ার্ড বদলালে অন্য সব সেশন বন্ধ, পাসওয়ার্ড bcrypt hash-এ রাখা, চাইলে fingerprint/passkey। ⚠️ (জেনেশুনে নেওয়া ঝুঁকি)
Two-factor (2FA/MFA) আছে? সাধারণ লগইনে TOTP/SMS 2FA নেই। বিকল্প: Passkey/Fingerprint লগইন (ফোনে hardware-সুরক্ষিত), মোবাইলে "একটি ফোন" নিয়ম, ই-স্বাক্ষরে ইমেইল OTP। ⚠️
পাসওয়ার্ড ভুলে গেলে? ইমেইলে ৬ অঙ্কের কোড (১৫ মিনিট, ৫ চেষ্টা) অথবা HR অস্থায়ী পাসওয়ার্ড দেয়। দুটোতেই পুরোনো সব সেশন বন্ধ। কে অ্যাকাউন্ট আছে তা বোঝা যায় না। ✅
লগইন কতক্ষণ থাকে? ওয়েবে ১২ ঘণ্টা বা ৬০ মিনিট নিষ্ক্রিয় হলে শেষ; অ্যাপে ৭ দিন বা ৩ দিন না খুললে। Superadmin বদলাতে পারে। ✅
চাকরি ছাড়লে বা সন্দেহ হলে লগইন বন্ধ হয়? হ্যাঁ। ব্লক, পদত্যাগ/বরখাস্ত কার্যকর, বা Superadmin-এর "sign out" হলে সব সেশন সঙ্গে সঙ্গে বন্ধ (প্রতি রিকোয়েস্টে যাচাই)। ✅
পাসওয়ার্ড বদলালে চুরি যাওয়া সেশনের কী হয়? বাকি সব সেশন বন্ধ হয় (যে সেশন থেকে বদলানো সেটা থাকে)। ✅
Single Sign-On আছে? 360 ERP-এর সাথে SSO হস্তান্তর আছে (সার্ভার-টু-সার্ভার, গোপন চাবি ব্রাউজারে যায় না)। অন্য Identity Provider (Azure AD, Google) নেই। ⚠️

খ. অনুমতি ও গোপনীয়তা

প্রশ্ন উত্তর অবস্থা
কর্মী কি অন্যের SIM/ID card request দেখতে বা নিজে issue করতে পারে? না। কর্মী শুধু নিজের request দেখেন ও বাতিল করেন (সুইচ ডিফল্টে বন্ধ); issue বা turn down শুধু HR Operations-এর আলাদা requisitions layer দিয়ে, যা ডিফল্টে কারও নেই। নতুন joiner-এর request-এর route শুধু onboarding login খুলতে পারে, আর approve না হওয়া পর্যন্ত কিছু issue হয় না। ✅
HR Operations-এর Quick reports (probation, joiner, transfer, resignation, ধর্ম) আর Admin Dashboard-এর "HR reports" কার্ড কে দেখতে পারেন? শুধু যাঁর HR Operations module আর তার quick_reports layer আছে (Superadmin সবসময়)। Layer-টা শুধু দেখার, তাই HR Operations-এ কোনো layer টিক না থাকলে default-এ পান; layer টিক করা থাকলে এটাও টিক থাকতে হয়। না থাকলে কার্ড, tab, menu লুকানো আর /api/hr-ops/quick/* 403 দেয়। এই রিপোর্টে কোনো টাকার অঙ্ক নেই। টেস্ট: docs/test-logs/2026-11-12/scripts/quick-api.mjs, quick-ui.mjs। ✅
Quick reports-এর Overtime (OT) রিপোর্ট কে দেখেন? যাঁর HR Operations-এর quick_reports আর quick_ot দুটোই আছে (Superadmin সবসময়)। যাঁদের আগে Quick reports ছিল তাঁরা একবার quick_ot পেয়েছেন; Module Access থেকে খুলে নেওয়া যায়। না থাকলে কার্ড/chip লুকানো, /api/hr-ops/quick/overtime 403, summary-তে OT নেই। শুধু ঘণ্টা, টাকা নয়। ✅
অপেক্ষায় থাকা আবেদনের বিস্তারিত (Admin Dashboard-এর টাইল, Pending Approvals, bell, Stuck) কে দেখেন? যিনি চেয়েছেন, chain-এর approver, Approvals module-এর Admin, আর ঐ আবেদনের নিজের module যাঁর আছে (যেমন Advance → Payroll, Asset → Asset Management); বাকিরা 403 — UI-তে নাম দেখলেও বিস্তারিত আসে না। HR Action / Exit-এ আগের কড়া নিয়ম। ✅
কেউ AI Assistant-কে বারবার প্রশ্ন করে Gemini-র বিল বাড়াতে বা সার্ভার ব্যস্ত রাখতে পারে? না। প্রতি account মিনিটে ২০ ও ঘণ্টায় ২০০ প্রশ্ন, কণ্ঠে মিনিটে ১০, পড়ে শোনানো মিনিটে ৩০ টুকরো, আর সবাই মিলে মিনিটে ১২০ — তারপর 429 "একটু ধীরে… পর আবার চেষ্টা করুন" (Retry-After)। Superadmin-ও এই সীমায়। সংখ্যা .env-এ বদলানো যায়। টেস্ট (১২ নভেম্বর): একজনের ২৫টা দ্রুত প্রশ্নে ২০টা 200, তারপর 429; ঘণ্টা-সীমা ও দুজন মিলে global সীমাও পরীক্ষিত। ✅
কাউকে Superadmin কে বানাতে পারেন? যিনি আগে থেকেই User/Admin, তাঁকে? শুধু system owner, Platform → Workspaces → Superadmins থেকে। ঐ workspace-এর কারও email দিলে তাঁর পুরনো account-ই Superadmin হয় (পাসওয়ার্ড একই, সব sign-in শেষ — আবার লগইন করতে হয়); অন্য workspace-এর account দেওয়া যায় না; সাধারণ Superadmin বা Admin কাউকে Superadmin করতে পারেন না (403)। টেস্ট (১৪ নভেম্বর): পুরনো account → Superadmin, পুরনো token 401; আবার → "already"; অন্য workspace → আটকায়; system owner নন → 403। ✅
কে কী দেখবে তা কীভাবে নিয়ন্ত্রণ হয়? তিন ভূমিকা (Superadmin/Admin/কর্মী) + ৪০ মডিউল + মডিউলের ভেতরে layer + বিভাগ-সীমা + কোম্পানি-সীমা। সব সার্ভারে প্রয়োগ হয় (UI লুকানো ছাড়াও API বন্ধ)। ✅
বেতনের তথ্য কে দেখে? শুধু Payroll মডিউলের Admin। কর্মী শুধু নিজের payslip। টেস্টে কর্মী অন্যের payroll খুলতে পারেনি। ✅
লোনের টাকা কে দেয়, কীভাবে প্রমাণ থাকে? অনুমোদনের পর লোন "Waiting for payment" থাকে, বেতন থেকে কাটা হয় না। শুধু Accounts Pay layer-ধারী (বা Superadmin) টাকা দিয়ে "Mark as paid" দেন — তারিখ, মাধ্যম, reference সহ; বেতনের বাইরে ফেরতও তাঁরাই গোনেন। প্রতিটা ধাপ (কে, কবে, কত, কীভাবে) loan_events-এ, কর্মী নিজের History দেখেন। LoanPlan.ts, টেস্ট docs/test-logs/2026-11-09/scripts/loan-payout-plan.mjs (৪০/৪০)। ✅
একজন একাই বেতন বানিয়ে পরিশোধ করতে পারে? না। HR বানায় → Audit অনুমোদন → Accounts পরিশোধ। যে বেতন চালিয়েছে/বদলেছে বা submit করেছে সে অনুমোদন দিতে পারে না; যে চালিয়েছে, submit বা অনুমোদন করেছে সে পরিশোধ করতে পারে না। Audit/Accounts "View only" layer পায় (দেখে, বদলাতে পারে না)। Audit Manager টেস্ট ৪৯/৪৯ পাস (test-logs/2026-10-25/06-audit-manager-retest.log)। ব্যতিক্রম: Superadmin। ⚠️
পদাধিকার বাড়িয়ে নেওয়া যায়? কর্মী নিজের role বাড়াতে পারে না; Admin নিজেকে বেশি মডিউল দিতে পারে না; API দিয়ে নতুন Superadmin বানানো যায় না (সবই টেস্টে যাচাই)। ✅
একাধিক কোম্পানির ডাটা আলাদা থাকে? হ্যাঁ, কোডে প্রতিটি SQL-এ কোম্পানির ফিল্টার বসে। (ডাটাবেস-স্তরে আলাদা স্কিমা নেই, একই ডাটাবেসে।) ⚠️
ব্যক্তিগত তথ্য (NID, ঠিকানা) কে দেখে? Employees মডিউলের Admin সব কর্মীর NID দেখেন — নীতি ঠিক করা দরকার। ফোন নম্বর: Employee Directory, Chat-এর contact info আর AI Assistant-এর "সহকর্মী খোঁজা" শুধু অফিসের Contact No. (all_employees.phone) দেখায়; ব্যক্তিগত মোবাইল (all_employees.mobile, Personal Contact) API থেকেই পাঠানো হয় না, থাকে শুধু Admin Panel -> Employees-এ (EmployeeDirectoryRoutes.ts, ChatRoutes.ts, AiAssistantRoutes.ts)। ⚠️
Employee Tracking-এ কে কার লোকেশন দেখে? Module Access-এ প্রতিটা অ্যাকাউন্টের জন্য বিভাগ আর একক কর্মী বাছা যায়; বাছা থাকলে সার্ভার শুধু তাঁদের লোকেশন, ইতিহাস, Stay Report ও Live Follow দেয়, অন্য কারও id দিলে 403। কিছু বাছা না থাকলে মডিউলের সবাইকে দেখে (আগের মতো); Superadmin সবসময় সবাই। ✅
একই ফোনে অন্য account-এ ঢুকলে আগের জনের ছবি বা তথ্য দেখায়? না। নিজের profile ছবির URL আর browser-এ cache হয় না, আর account বদলালেই আগের ছবি মুছে যায়। ✅
কেউ কি নিজের profile ছবি যা খুশি বদলে দিতে পারে? না। নতুন ছবি Superadmin-এর অনুমোদনের অপেক্ষায় থাকে, ততক্ষণ পুরনো ছবি দেখায়; Superadmin পুরনো-নতুন পাশাপাশি দেখে Approve বা কারণসহ Reject করেন। অনুমোদনের API শুধু Superadmin-এর (টেস্টে অন্য admin 403)। ✅
Payroll-এ MD অ্যাপ ব্যবহার না করলে তাঁর অনুমোদনের প্রমাণ কী? Recruitment থেকে candidate-কে email কে পাঠাতে পারে, ভুল জায়গায় যেতে পারে কি? শুধু Recruitment-এর Email candidates অনুমতি যাঁর আছে (আলাদা টিক, কাউকে আপনাআপনি দেওয়া হয় না; Superadmin সবসময়) — বোতাম লুকানো আর API-তে 403। ঠিকানা নেওয়া হয় candidate-এর রেকর্ড থেকে, ব্যবহারকারী অন্য ঠিকানা দিতে পারেন না; বিষয়ের লাইনে নতুন লাইন বাদ দেওয়া হয় (header injection নয়), লেখা HTML-escape হয়ে যায়। প্রতিটি email candidate_emails-এ থাকে (RecruitmentRoutes.ts)। ✅

কীভাবে উত্তর দেবেন (পরামর্শ)

  1. সবসময় প্রমাণ দেখান: "আমরা নিরাপদ" বলার বদলে ফাইলের নাম বা টেস্ট লগ দেখান।
  2. যা নেই তা স্বীকার করুন এবং তারিখসহ পরিকল্পনা দিন। ❌ ও ⚠️ সারি ধরে একটি কর্মপরিকল্পনা বানিয়ে রাখুন।
  3. "হোস্টিং-নির্ভর" (🏢) প্রশ্নে আপনাদের সার্ভার প্রদানকারীর নথি (ডাটা সেন্টার, ব্যাকআপ, TLS) আলাদা দেখাতে হবে।
  4. অডিট আসার আগে: CORS_ORIGINS সেট, পাসওয়ার্ড নীতি নিয়ে লিখিত সিদ্ধান্ত (সহজ পাসওয়ার্ড কেন), ~~অব্যবহৃত GPL লাইব্রেরি বাদ~~ (✅ হয়ে গেছে), ব্যাকআপ পরীক্ষা (একবার পুনরুদ্ধার করে দেখা), penetration test বুক করা। এগুলো সবচেয়ে কম খরচে সবচেয়ে বেশি প্রশ্নের উত্তর বদলে দেয়।

প্রশ্ন: .env-এ CORS_ORIGINS দেওয়ার পরও সার্ভার "CORS_ORIGINS is not set" দেখাচ্ছিল কেন? উত্তর: .env লোড হওয়ার আগেই WebSecurity.ts মানটা পড়ে ফেলত, তাই তালিকা খালি ধরে নিয়ে CORS সবার জন্য খোলা রাখত। এখন .env সবার আগে লোড হয়, তাই তালিকাটা সত্যিই কাজ করে: তালিকার বাইরের সাইট API-র উত্তর পড়তে পারে না।

প্রশ্ন: কোনো কর্মী ওয়েবসাইটে যা পারেন, মোবাইল অ্যাপে কি তার চেয়ে কম দেওয়া যায়? উত্তর: হ্যাঁ। Module Access-এ প্রতিটা module আর Self Service switch-এর আলাদা App switch আছে, আর পুরো অ্যাপ বন্ধ করার একটা মূল switch। অ্যাপ কখনো ওয়েবসাইটের চেয়ে বেশি পায় না। এটা শুধু menu লুকানো না: অ্যাপের token দিয়ে বন্ধ module-এর API ডাকলে সার্ভার 403 দেয়, আর অ্যাপ বন্ধ থাকলে login-ই হয় না (AppAccess.ts)। নতুন অ্যাকাউন্টে অ্যাপ ডিফল্টে বন্ধ; প্রতিটা বদল access audit-এ থাকে।

প্রশ্ন: কল চলাকালে নেট কেটে আবার ফিরলে কেউ কি অন্যের কলে ঢুকে পড়তে পারে? উত্তর: না। কল ধরে রাখার ৩০ সেকেন্ডে ফিরে আসতে call:rejoin লাগে, আর server সেটা শুধু সেই কলের caller বা callee-র নিজের লগইন করা account থেকে নেয় (socket-এর token যাচাই করা user id দিয়ে, CallRoutes.ts)। অন্য কেউ চাইলে "This call has ended." পায়। কলের media আগের মতোই সরাসরি দুই ফোনের মধ্যে encrypted (DTLS-SRTP) থাকে।

প্রশ্ন: অ্যাপ বন্ধ অবস্থায় কল কাটার (Decline) route-এ sign-in লাগে না কেন, এটা কি ঝুঁকি? উত্তর: ফোনের কল-পর্দা অ্যাপ খোলা ছাড়াই চলে, তাই সেখানে sign-in token থাকে না। তার বদলে প্রতিটা কলের জন্য আলাদা ৪৮-অক্ষরের এলোমেলো চাবি তৈরি হয়, যা শুধু callee-র নিজের ফোনের push-এ যায়। চাবি ছাড়া বা ভুল চাবিতে কিছু হয় না; ঠিক চাবিতেও শুধু সেই বাজতে থাকা কলটা Decline হয় — কোনো ডাটা পড়া বা বদলানো যায় না (CallRoutes.ts)।

প্রশ্ন: Claim-এর না পাঠানো খসড়া ফোনে থাকে — একই ফোনে অন্য কেউ login করলে কি তা দেখতে পায়? উত্তর: না। খসড়া (src/lib/formDraft.ts) প্রতিটা account-এর আলাদা চাবিতে থাকে, তাই অন্য login সেটা পড়ে না; sign-out করলেই সব খসড়া মুছে যায়, পাঠালে বা ৩ দিন পরেও মুছে যায়। খসড়ায় শুধু নিজের লেখা থাকে (ফাইল নয়), আর পাঠানোর সময় server আগের মতোই সব অনুমতি ও হিসাব যাচাই করে — খসড়া কিছুই অনুমোদন করে না।

প্রশ্ন: "Conveyance Bill Claim" থেকে "Bill Claim" নাম বদলানোর পর কেউ কি অনুমতি হারায় বা বাড়তি পায়? উত্তর: না। Server চালু হওয়ার সময় (billClaimRename.ts) আগে দেওয়া প্রতিটা অনুমতি একই মানুষের কাছে নতুন নামে সরে যায়: Admin module conveyance → bill_claim, তার layer, Data Import-এর import_conveyance → import_bill_claims, Self Service switch can_view_conveyance_claims → can_view_bill_claims, App access আর Access Template-এর টিক। নতুন কিছু দেওয়া হয় না। পুরনো API (/api/user-claims) আর নেই, নতুন /api/bill-claims আগের মতোই module / layer / switch যাচাই করে।

প্রশ্ন: Approval-এর Details-এ কি যে কেউ অন্যের আবেদন (ছুটির কারণ, টাকার অঙ্ক, ফাইল) দেখতে পারে? উত্তর: না। দেখতে পারেন শুধু যিনি চেয়েছেন, ঐ আবেদনের approval chain-এর লোকেরা (আগের, এখনকার বা পরের Layer-এর approver, Supervisor / Head, ad-hoc approver, ছুটির Reliever, Exit clearance-এর approver), Approvals module-ওয়ালা Admin আর Superadmin — server প্রতিবার যাচাই করে (ApprovalDetailsRoutes.ts), সংযুক্ত ফাইলেও একই নিয়ম। অন্য কেউ id বদলে চাইলেও 403 পান। HR Action ও Exit আলাদা নিয়ম: এগুলো কারও সম্পর্কে নেওয়া সিদ্ধান্ত, তাই যাঁর সম্পর্কে তিনি নিজে খুলতে পারেন না (অপেক্ষায় থাকা separation / demotion / increment, বা HR-এর খোলা termination) — শুধু নিজের চাওয়া resignation দেখেন; শুধু Approvals module থাকলে এগুলো খোলে না — HR Action-এ HR Operations, Exit-এ Exit / Offboarding module লাগে (chain-এর লোক ছাড়া); HR Action-এর বেতন ("Now → Becomes") দেখেন শুধু Superadmin, যিনি তুলেছেন, তার approver-রা আর Payroll-এর "See salary amounts" যাঁর আছে, বাকিদের *****। টেস্ট: docs/test-logs/2026-11-12/scripts/details-access-api.mjs।

প্রশ্ন: HR কারও termination বা increment নিয়ে ভাবছে — কর্মী কি Details দিয়ে আগেই দেখে ফেলতে পারেন? উত্তর: না। HR Action বা HR-এর খোলা Exit যাঁর সম্পর্কে, তিনি সেটা খুললে 403 পান (id বদলে চেষ্টা করলেও)। নিজের resignation আর নিজের অন্য আবেদন আগের মতোই দেখেন।

প্রশ্ন: PEPM-এ একজন কি অন্যের তোলা MPR entry দেখতে বা বদলাতে পারে? উত্তর: একই প্রজেক্টের team-এর হলে হ্যাঁ — যাদের একটা প্রজেক্টের permission দেওয়া, তারা সেই প্রজেক্টের সব entry দেখে ও আগের নিয়মে বদলায় (আগে এক প্রজেক্ট account ভাগ করে যেমন হতো), প্রতিটা সারিতে কে দিয়েছে লেখা থাকে। অন্য প্রজেক্টের entry Self Service-এ দেখা বা বদলানো যায় না; সেটা শুধু Admin Panel → PEPM Reports-এ, Reports module-এর Read / Edit / Delete layer থাকলে (Superadmin সবসময়)। শুধু Admin role যথেষ্ট নয়। প্রজেক্ট তুলে নিলে ঐ প্রজেক্টের entry-র অধিকারও যায়। সব যাচাই server-এ (EntriesRoutes.ts, PepmTeam.ts)।

প্রশ্ন: কারো Budget (PEPM) switch বন্ধ থাকলে সে কি API দিয়ে Budget বা MPR No-র তালিকা পড়তে পারে? উত্তর: না (৭ নভেম্বর ২০২৬ থেকে)। আগে menu লুকাত কিন্তু /api/budgets, budget item, MPR No, Job-এর তালিকা যেকোনো login করা account পেত — পুরো-অ্যাপ টেস্টে ধরা পড়ে। এখন requireBudgetRead শুধু Superadmin, Budget switch চালু, Job Edit, আর PEPM module (Imports, MPR Nos, Reports, Projects) থাকা Admin-কে দেয়; বাকিরা 403। Admin Dashboard-ও এখন শুধু দেওয়া module-এর tile দেখায় ও তার ডাটাই চায়।

প্রশ্ন: অফিসের সবাই একই internet (একই IP) থেকে আসেন। কয়েকজনের ভুল password-এ কি পুরো অফিস আটকে যাবে? আর কেউ কি আমার ID-তে ইচ্ছে করে ভুল দিয়ে আমাকে আটকে রাখতে পারে? উত্তর: যাঁরা আগে এই ফোন / browser থেকে সফলভাবে login করেছেন, তাঁরা আটকাবেন না। সফল login-এর পর ডিভাইসটা ওই account-এর জন্য একটা সই করা token পায় (চেনা ডিভাইস, LoginGuard.ts)। পরের login-এ সেটা থাকলে network-এর ৩০-বার আর account-এর ৫-বার লক ওই ডিভাইসে খাটে না; শুধু ডিভাইসের নিজের সীমা (১৫ মিনিটে ১০ বার ভুল)। অচেনা ডিভাইস (নতুন ফোন, অন্য কারো কম্পিউটার) আগের নিয়মেই আটকায়, তাই password অনুমান আগের মতোই কঠিন। Token নকল বা বদলানো যায় না (HMAC), অন্য account-এ কাজ করে না, ১৮০ দিন পরে বা password বদলালে বাতিল হয়।

প্রশ্ন: কেউ chat-এ disappearing messages চালু করে কথোপকথনের প্রমাণ মুছে ফেলতে পারে কি? উত্তর: শুধু তাঁরাই পারেন যাঁদের Superadmin Module Access-এ "Disappearing messages" switch দিয়েছেন — শুরুতে কারোরই নেই। switch ছাড়া অপশনটা দেখায় না, আর server-এ চাইলেও 403 আসে (ChatRoutes.ts)। বন্ধ করা সবসময় যায়। কোনো switch না দিলে কোম্পানির সব chat-এর রেকর্ড থাকে।

প্রশ্ন: কল চলার সময় অ্যাপ থেকে বের হলে কি অ্যাপ গোপনে মাইক বা ক্যামেরা চালু রাখে? উত্তর: শুধু চলমান কলের সময়, আর তখন সবসময় একটা "Call in progress" notification দেখা যায় (CallService.java)। Android-ও নিজের মাইক/ক্যামেরা চিহ্ন দেখায়। কল শেষ হলে বা notification-এর Hang up চাপলে service বন্ধ হয়ে যায়। কল ছাড়া এই service কখনো চলে না।

প্রশ্ন: 360 ERP থেকে CredenceHR-এ password ছাড়া ঢোকা যায় — কেউ কি এটা দিয়ে অন্যের account-এ ঢুকে পড়তে পারে? উত্তর: link বানাতে পারে শুধু সেই application-এর (360 ERP বা Superadmin যাকে যোগ করেছেন) সার্ভার, Superadmin-এর দেওয়া তার নিজের App ID ও Secret দিয়ে, HTTPS-এ, আর চাইলে শুধু তার IP থেকে। মানুষ মেলে email আর Employee ID দুটো দিয়েই। link একবারই চলে আর দুই মিনিটের মধ্যে মেয়াদ শেষ হয়। ঢোকার পর password sign-in-এর মতোই সব যাচাই হয় (block, App access, ফোনের সীমা)। প্রতিটা চেষ্টা log-এ থাকে (Active Users → Partner app sign-in)। secret হারালে বা সন্দেহ হলে সেই application-এর "New secret" চাপলে আগেরটা সাথে সাথে অকেজো হয়; "Switched on" বন্ধ বা "Remove" করলে শুধু সেই application বন্ধ হয়, বাকিগুলো নয়।

প্রশ্ন: Check In/Out দ্রুত করতে ফোন আগের অবস্থান মনে রাখে — তাহলে কি পুরোনো জায়গা থেকে check-in করা যায়? উত্তর: না। শেষ অবস্থান (credence_last_fix) শুধু map কোথায় খুলবে তা ঠিক করে; Check In / Check Out-এ পাঠানো অবস্থান সবসময় নতুন GPS fix (ফোনের নিজের, সর্বোচ্চ ৩০ সেকেন্ড পুরোনো)। শেষ অবস্থান ১২ ঘণ্টা পর বাদ, logout-এ মুছে যায়, তাই একই ফোনে অন্য কেউ login করলে আগের জনের জায়গা দেখে না। Map-এর ছবি (tile) ফোনে জমা থাকে, কিন্তু তাতে কারও তথ্য নেই।

প্রশ্ন: Payroll-এর কাজ করেন কিন্তু বেতন দেখার কথা নয় — তিনি কি কোনোভাবে অঙ্ক দেখতে পারেন? উত্তর: না, যদি "See salary amounts" টিক না থাকে। অঙ্ক লুকানো হয় সার্ভারে, পাঠানোর আগেই — তাই পর্দা, Excel / PDF, AI Assistant বা সরাসরি API, সব জায়গায় *****। তিনি Payroll-এ কিছু বদলাতেও পারেন না, আর HR Operations report-এ Salary কলাম পান না। নিজের payslip তিনি আগের মতোই দেখেন।

প্রশ্ন: Admin Dashboard থেকে একসাথে অনেক হাজিরা approve করলে কি কেউ এমন কিছু approve করতে পারে যা তাঁর approve করার কথা নয়? উত্তর: না। যে সারি তিনি একা approve করতে পারতেন না, সেখানে tick box-ই আসে না; আর "Approve selected" প্রতিটা সারির জন্য আগের একক approve-এর API ডাকে, যা প্রতিবার যাচাই করে — Approval Workflow-এ শুধু যাঁর ধাপ বা Superadmin, workflow-এর বাইরের সংশোধনে Attendance module। কেউ API সরাসরি ডাকলেও 403।

প্রশ্ন: Data Import দিয়ে কি কোনো employee-কে Superadmin বা Admin-এর login-এর সাথে জুড়ে দেওয়া যায়? উত্তর: না। মোছা employee আবার import করলে শুধু এই group-এর সাধারণ (user) login-এ, Employee ID হুবহু Login ID হলে, আবার যুক্ত হয় (Employees তালিকা বা Tracking খুললেও একই নিয়মে নিজে থেকে জোড়ে)। email বা নাম মিললে নিজে থেকে নয়, Employees → Unlinked logins-এ মানুষ নিশ্চিত করে। Admin বা Superadmin-এর login ID দিয়ে সারি দিলে আটকায় ("already the Login ID of …")। এমন জোড়া লাগাতে হলে Users থেকে হাতে করতে হয়।

প্রশ্ন: Management Dashboard দিলে কি সে বেতনের মোট খরচও দেখে?

উত্তর: না, যদি আলাদা করে "Money" layer টিক না দেওয়া হয়। Dashboard-এর প্রতিটা অংশ (People, Attendance, Money, Approvals, Projects & Targets, Recruitment, Fleet & assets) Module Access-এ আলাদা টিক; যেটা নেই server সেই সংখ্যা পাঠায়ই না, AI Assistant-ও বলে না। Money শুধু টিক দিলে।

প্রশ্ন: কর্মী কি নিজের Login ID (username) বদলে ফেলতে পারেন? উত্তর: শুরুতে না — Profile-এ Change Username দেখায় না, আর server-ও (PUT /api/profile/username) ফিরিয়ে দেয়। Superadmin চাইলে Admin Panel → Users → Password requests-এ "Let people change their own username" চালু করতে পারেন; তখন বর্তমান password দিয়ে বদলানো যায়। বন্ধ থাকলে দরকারে HR Users থেকে বদলে দেয় (Users module-এর Edit/Add layer লাগে)।

প্রশ্ন: "Their Branch" দিলে কেউ কি অন্য Branch-এর project-এ হাজিরা দিতে পারবেন? না। প্রতিটা check in / out আর Correct Attendance-এ server নিজেই কর্মীর Employee record-এর Branch থেকে Project বের করে (checkInProjectsFor, AttendanceProjects.ts), app-এর পাঠানো project মানে না। Branch-এ Project যুক্ত না থাকলে কোথাও হাজিরা হয় না। এই অপশন শুধু Users module-এর edit_add layer আছে এমন Admin চালু করতে পারেন; কর্মীর Branch বদলানো যায় Employees module থেকে, তাই দুটো আলাদা অনুমতির ভেতরে থাকে।
